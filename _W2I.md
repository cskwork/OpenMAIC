# W2-I — image, video and pptx import agent tools

## Scope

Ported three agent tools from the reference implementation into this repo. The
provider substrate was already present — `lib/media/image-providers.ts`,
`lib/media/video-providers.ts`, the adapters under `lib/media/adapters/`, the
`@openmaic/importer` package, and the server-side model resolvers
(`resolveImageModel` / `resolveVideoModel` in `lib/server/provider-config.ts`).
Only the agent tools that wrap them were missing; this change ports them:

- `generate_image` — `lib/server/agent-runtime/generate-image.ts`
- `generate_video` — `lib/server/agent-runtime/generate-video.ts`
- `import_pptx` — `lib/server/agent-runtime/import-pptx.ts` plus
  `import-pptx-worker.mjs`, `pptx-mime.ts` and `node-xhr.ts`

## Per-tool port notes

### generate_image

- Schema: `stageId`, `prompt`, optional `aspectRatio` (`16:9` / `1:1` / `4:3`,
  default `16:9`) and optional `styleHint` (appended to the prompt as a style
  direction before sizing).
- Provider selection: the first server-configured image provider, or
  `DEFAULT_IMAGE_PROVIDER` when that env names a configured provider. Unknown
  or unconfigured providers produce clear error results (`no server image
  provider is configured` / `DEFAULT_IMAGE_PROVIDER=… is not configured`).
- Server-side model resolution: `resolveImageModel(providerId)` is
  authoritative — the tool never accepts a caller-supplied model. A provider
  whose catalog declares models fails loud when the server resolves none
  (`reason: missing-model`) instead of silently falling back to an adapter
  default. Model-less providers (empty catalog, e.g. workflow-driven local
  runners) are left to resolve their own target at call time.
- Bounds: `GENERATE_IMAGE_TIMEOUT_MS = 300_000`; generated bytes capped by
  `MAX_REMOTE_IMAGE_BYTES` (20 MB) with the `MAX_REMOTE_IMAGE_BATCH_BYTES`
  (100 MB) aggregate download budget; every download hop passes the SSRF guard
  and is capped at 5 redirects.
- Usage: `recordGenerationUsage({ kind: 'image', unit: 'image', quantity: 1 })`,
  fire-and-forget (the neutral counterpart of the reference's call logger).

### generate_video

- Schema: `stageId`, `prompt`, optional `aspectRatio` (six values), optional
  `durationSec` and optional `resolution` (`480p` / `720p` / `1080p`). Options
  are normalized against the provider's capabilities with
  `normalizeVideoOptions`.
- Capability gate: the tool is registered **only** when
  `hasConfiguredVideoGeneration()` is true — a server-configured video
  provider that exists in `VIDEO_PROVIDERS` and, when it requires a key, has
  one. `buildCourseAllowlist` follows the same gate, and the runner derives
  its allowlist from the registered toolset, so an unconfigured deployment
  never hands the model a tool that can only throw. Call-time selection
  mirrors the gate.
- Server-side model resolution like `generate_image` (fail loud with
  `reason: missing-model`).
- Bounds: `GENERATE_VIDEO_TIMEOUT_MS = 15 * 60_000` (the longest provider poll
  budget) and `MAX_GENERATED_VIDEO_BYTES = 200 * 1024 * 1024`; SSRF-guarded
  download with a 5-redirect cap; `awaitWithSignal` makes a caller abort reject
  an in-flight provider call even when the adapter ignores the signal.
- Usage: `recordGenerationUsage({ kind: 'video', unit: 'second',
  quantity: duration })`.

### import_pptx

- Layout-preserving import: parse the uploaded `.pptx` source material into DSL
  slides and write one scene per slide, appended after the stage's pages or
  inserted at `atOrder` (same shift semantics as `edit_deck` insert /
  `duplicate_scene`). The stage keeps its identity — `create_stage` owns the
  title, the PPT never touches it.
- Worker isolation: `parsePptxIsolated` spawns `import-pptx-worker.mjs` in a
  worker thread so linkedom's `document`/`Node` shims never land on the
  request process (`typeof document` stays `undefined` for concurrent SSR).
  `node-xhr.ts` provides the Node-side `XMLHttpRequest` shim the importer's
  bundled pdfjs/stream-http expect when tests parse on the request process.
- Idempotency: the outline `requirement` and the per-stage `pptxImports`
  receipt map are keyed by `import_pptx:sha256:<content digest>`, with the
  legacy `import_pptx:<materialId>` key still consulted inside the map. A
  retry of the same deck — even re-uploaded as a new `mat_` id — reports the
  pages it already imported instead of appending a second copy; if every
  imported page was deleted, the retry is a genuine fresh import. The first
  write of a `pptxImports` map migrates a legacy `requirement` receipt so a
  later retry of that material stays a report. Determinism derives from the
  deck's content digest (stable across re-uploads), so the same material
  replay always lands on the same receipt. The session-material row carries no
  digest, so the sha256 is computed from the deck bytes at import time — one
  extra registry read placed *before* the receipt check, keeping the expensive
  parse off the already-imported path.
- Bounds: `MAX_IMPORT_SLIDES = 80` — oversized decks are truncated and the
  truncation is reported (`truncated`, `sourceSlideCount`).
- Extracted media: the worker embeds deck media as data URLs; the main process
  rewrites them through `defaultUploadImportedMedia`, which persists each blob
  in the asset registry and falls back to the original data URL when the
  upload throws, so a rejected upload never aborts the deck parse.
- Cross-owner isolation: the tool writes only through the run's owner-bound
  store (the same store every stage tool uses); the schema exposes no
  ownership parameter, and a stage the store cannot see reads as
  `no-document` — never minted or written.

## What was stripped, and how the neutral substitute works

- **Billing / usage charging** (`runBilledCall` / `logMediaCall`): no usage-cost
  accounting exists here. The call-logger metadata those wrappers fed is gone;
  `recordGenerationUsage` (image/video usage events) is kept as the neutral
  counterpart.
- **The live OSS byte path** (`isStorageConfigured` / `getStorageProvider` /
  `isHostedOnOurStorage` and the local classroom-media file fallback):
  generated image/video bytes and pptx media are persisted through the shared
  **asset registry** — `getServerPersistenceProvider(…).assetStore.put({ key:
  'shared' }, blob, { contentType })` — the same neutral surface
  `use_material_media` and the TTS path use. The returned registry id is the
  stable `src` the agent writes into slide media elements; the renderer
  resolves registry ids to serving URLs at display time. Provider-hosted URLs
  are always materialized into the registry (there is no "already on our
  storage" pass-through), which also keeps expiring provider download URLs
  durable.
- **Vendor-specific branches**: `applyVideoModelDefaults` (a managed
  Seedance-2.0-Fast deployment default) is not ported — `normalizeVideoOptions`
  alone is the neutral path. No provider identifier appears in the tool layer;
  model choice comes exclusively from the server config resolvers.

## Gating conditions

- `generate_video` is capability-registered: `hasConfiguredVideoGeneration()`
  is true iff some server-configured video provider id exists in
  `VIDEO_PROVIDERS` and (the provider does not require a key, or its resolved
  config has an API key). Both `buildDslCourseToolset` and
  `buildCourseAllowlist` follow it; the runner's `allowedToolNames` is derived
  from the registered `dslTools` group, so the allowlist tracks registration
  automatically.
- `generate_image` and `import_pptx` are always registered and degrade at call
  time with explicit error results (`no server image provider is configured`,
  `no model is configured …`, `no-document`, `not_found`, `not_source`,
  `unsupported_type`, …) — the reference semantics.

## Tests

- `tests/agent-runtime/generate-image.test.ts`: schema validation; fails loud
  with no provider configured; fails loud with no server model (provider never
  called — never a silent adapter default); pre-aborted call; generate +
  persist through the asset registry (the `put` receives the decoded bytes and
  mime under `{ key: 'shared' }`); byte cap on inline base64; provider-hosted
  URL materialization.
- `tests/agent-runtime/generate-video.test.ts`: schema validation; capability
  gating (absent from the toolset and allowlist without a provider, registered
  with one); fails loud with no server model; submit/wait/persist/return media
  metadata; provider-URL materialization; 200 MB byte cap (declared
  content-length trips before buffering); provider error without fallback;
  timeout; abort of an in-flight provider call.
- `tests/agent-runtime/import-pptx.test.ts`: helper coverage (pptx detection by
  mime or filename, title from first text element, speaker notes → speech,
  byte-exact importer HTML, stage-wide outline numbering); registration +
  allowlist + prompt-block mention; append / atOrder insert / snapshot-outline
  shift / clamp; idempotent replay; re-upload of the same deck is the same
  import; stage identity preserved; no `replace` parameter; owner-bound-only
  writes (a foreign stage reads as `no-document`, the schema exposes no
  ownership parameter); missing / non-source / non-pptx materials; truncation
  at 80 slides and abort; session-materials prompt block; worker isolation
  (constructable `XMLHttpRequest` shim, no `window`/`document` on the request
  process, real decks parse in a worker); legacy receipt migration on the first
  `pptxImports` write.
- Updated registration pins: the runner voice/skills/web-search registration
  tests and the DSL wiring test now include `import_pptx` and `generate_image`
  in the exact ordered toolset and sorted allowlist; `generate_video` stays
  absent in the test environment (no video provider configured).
